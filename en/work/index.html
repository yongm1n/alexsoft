OPEN SOURCE · SOFTWARE INTELLIGENCE

Cascade — an engine that reads code and maps screens to database columns

“If this column changes, which SQL statements, service methods, APIs and screens are affected?” ALEXSOFT designed and built a static-analysis engine to answer a question that often has no precise answer in older systems, using source code alone, and released it under Apache-2.0. The same answers appear in a viewer for people and an MCP server that AI coding agents can query directly.

Type
Open-source static-analysis engine · Local viewer · MCP serverPublished under Apache-2.0 · github.com/alexsoft-hq/Cascade
Questions answered
Column → SQL → Method → API → Screen: impact in both directionsFrom a column you plan to change to the screens it affects; from a screen you plan to open to the columns it reaches
Supported stack
Java Spring MVC · MyBatis (XML, annotations, Plus) · JPA/Spring Data · SQL DDL (MySQL, PostgreSQL, Oracle, H2) · JS/TS, Vue and React routers · OpenAPI · HARKotlin, GraphQL and connections resolved only at runtime are explicitly identified as unsupported
Principle
No claims beyond what the analysis provesVerified and inferred connections are marked separately; anything the analysis could not see is stated explicitly
Deployment
Runs entirely on your own computerSource code and analysis results stay local · Database connections read only table and column names, never the data
WHY

Change impact lived in people’s memories

Finding which screens will break when a column changes can take days. As AI coding agents increasingly make code changes, machines need to answer that question before editing.

HOW

Verified and inferred connections are shown separately

Connections that source code alone cannot establish are marked as unseen. The viewer for people and the answers sent to AI agents come from the same engine, keeping both consistent.

SO WHAT

Reconstruct legacy impact from the source

Finding how far a change reaches is often the longest part of legacy modernization and integration design. The same approach can map your systems.

Being explicit about what static analysis cannot answer makes the answers it can provide trustworthy.

OWN PRODUCT · HEALTHCARE DATA

ALEXSOFT Bridge — EMR and LIS data in Korean standard formats, with a reason for every unconverted record

Bridge converts data from hospital and clinic EMR and LIS (laboratory information systems) to Korea’s KR Core 2.0.0 format. KR Core is a set of rules published by HL7 Korea and based on HL7® FHIR®. Conversion encounters unapproved test codes, values with incompatible units and results referring to patients absent from the source. Silently skipping them leaves recipients unable to tell what is missing. Bridge reports a reason for every unconverted record.

Type
HL7® FHIR® KR Core interoperabilitySource data is read only and never modified
Account for every record
In scope = converted + excluded + failed · 0 records disappear without a reason9,313 synthetic source records, including 4,906 test results = 8,938 converted + 329 excluded + 46 failed · Processing stops without producing a report if the totals do not reconcile
Reasons for non-conversion
Excluded records are deliberately not generated under the rules; failed records cannot be generated because of source-data problemsExcluded: codes awaiting approval, orders without results, old results superseded by corrections · Failed: incompatible or missing units, duplicate results, missing issue times, references to absent patients · Download the records and their reasons as CSV
Rule validation
Automatically validated against the KR Core 2.0.0 rules published by HL7 Korea0 ERRORs across all 8,938 resources generated from synthetic source data · Validated with the HAPI FHIR validator

← Scroll sideways to see the full process →

WHY

Hospitals record the same information differently

One hospital may label a test RBC while another writes out “red blood cell count”; unit notation also varies. People can recognize the meaning, but systems cannot. A common format such as KR Core makes data from different hospitals readable in the same structure.

HOW

Keep every unconverted record with its reason

Records intentionally not generated under the rules, such as unapproved test codes, are excluded. Incompatible units or references to absent patients are failures. Every run checks that in scope = converted + excluded + failed, then automatically validates the converted output against KR Core rules.

SO WHAT

Start with one source and one area

We agree together which source to use and how much to convert. The same report shows what was converted and what remains, with the reason for each remaining record.

“Of 9,313 records, 8,938 were converted. The remaining 375 could not be converted for these reasons.” That is what completion needs to explain.
