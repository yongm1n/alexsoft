가족은 어떻게 로그인할까?

원안어르신별 ID·비밀번호 하나를 가족이 함께 사용. 개인 가입·연결 없음.
이전 AI가족별 계정 또는 대표 보호자 초대 방식.
이번 초안: 공용 계정 유지. 가족 한 명만 접근을 회수하기 어려운 한계는 별도로 표시합니다.

건강자료는 어디까지 담을까?

원안필요한 건강자료와 개별 안내를 중요메모·첨부로 전달.
이전 AI초기에는 일반 안내 위주로 줄이고 상세 건강기록은 별도 검토.
이번 초안: 건강자료 포함 유지. 실제 허용 자료와 제공 근거는 아직 정하지 않았습니다.

앱으로 만들까, 웹으로 시작할까?

사용자 결정웹부터 개발하고, 필요 확인 후 Flutter 앱. 처음부터 다양한 화면을 지원하는 API를 개발.
이전 AI직원 앱 + 가족 웹, 이후 운영 부담을 고려한 웹 시작 제안.
사용자 결정: 모바일 대응 웹 우선. 앱의 필요성이 확인되면 Flutter 앱을 개발·배포합니다. 웹과 앱은 공통 API를 사용합니다.

얼마나 보관하고, 어느 정도 올릴까?

목업게시 후 6개월 보관 ‘예정’.
이전 AI영상 30~60초·20~30MB, 월 19만원은 예시 계산.
현재: 기간 · 한도 · 비용 미정. 아래 시뮬레이션은 승인된 정책이나 견적이 아닙니다.
이번 설계에서 보완한 것: 관리자 셀프서비스, 게시 전 대상 확인, 첨부 일부 실패 시 비공개 유지, 접근 회수와 실제 삭제의 구분. 모두 검토 제안입니다.

이번 검토 MVP는 단일 센터의 공용 가족 계정, 직원 개인 계정, 담당 배정, 공간 관리, 메모·핀·건강자료, 사진·영상·PDF, 확대·다운로드, 공통 블로그 자동 갱신을 포함한다. 원안의 영상·건강자료는 유지하고 구체 허용 범위를 미정으로 남긴다.

원안에서 제외한 것은 일일 작성 의무와 실시간 대화다. 이번 설계에서 추가하지 않는 것은 가족별 가입/초대, 결제, 다중 센터 셀프 가입, 의료기록 전체 대체, AI 건강판단, 자동 얼굴 인식·모자이크, 기존 시스템 연동, 대량 전체 공지·직원 전용 자료다. 마지막 두 항목은 목업 확장이라 별도 범위 결정 대상이다. PPT는 목업에 있으나 허용 포맷 결정 전 기본 지원을 약속하지 않는다.

사용자는 2026-10-21 모바일 대응 웹을 우선 개발하고, 모바일 앱 필요성이 실제로 강하게 확인되면 Flutter 앱을 개발·배포하는 방향을 정했다(UD-08~09). Flutter 앱 착수 시점·지원 OS·스토어 일정, 세부 웹 기술·PWA 채택은 미정이다. 사용자 문장의 두 번째 ‘모바일 웹의 필요성’은 문맥상 ‘모바일 앱의 필요성’으로 이해한 것을 현재 대화에서 안내했다.

웹과 미래 Flutter 등 다양한 Presentation Layer가 사용할 공통 API Layer를 처음부터 설계한다(UD-10). 웹과 API를 기능 단위로 함께 개발하며 범용 API 플랫폼을 먼저 완성하는 계획이 아니다. API와 서버 업무규칙 재사용을 목표로 하되 미래 Flutter 화면·기기 연동·배포는 별도 개발이다. 재작업이 전혀 없다고 보장하지 않는다. 아직 웹 애플리케이션을 구현한 상태는 아니다. 클라우드, 운영비, 보관기간 등 나머지 미정 정책은 유지한다.

주요 동선과 상태

가족: 로그인 → 홈의 핀/최근 3건 → 전체 소식 또는 첨부 상세 → 확대·다운로드. 직원: 로그인 → 담당 목록 → 대상 선택 → 작성·파일 처리 → 대상·동반 인물·내용 확인 → 게시 결과. 관리자: 목록 → 상태·담당자 확인 → 변경 영향 확인 → 실행 → 결과/처리 중 구분.

업로드 일부 실패 시 성공 파일만 조용히 공개하지 않는다. 실패 항목을 제거하거나 재시도한 뒤 전체 준비 상태에서 다시 확인한다(이번 설계 제안). 공간 중단·권한 회수 후에는 작성 중인 자료도 새로 게시할 수 없다. 가족의 빈 화면은 이용 중단·통신 오류와 구분한다.

기술 고려사항

  • 어르신별 접근검사를 목록·상세·원본·썸네일·변환본·다운로드 모두에 적용한다.
  • 공개 파일 링크·비밀번호 평문 조회를 운영 편의 기능으로 추가하지 않는다.
  • 네이버 블로그 연계는 서버 측 피드 확인을 후보로 설계한다. 실제 RSS 제공 범위·갱신 간격·이미지 이용 조건을 검증해야 한다.
  • 웹우선 방향에 따라 실제 직원 기기의 사진 선택·전송 중단·복귀와 가족의 접근 동선을 웹에서 검증한다. 강한 앱 필요성이 확인되면 Flutter 전환 시점·기능을 결정한다. 푸시가 원안 필수라는 근거는 없다.
  • 웹 화면에 종속되지 않은 공통 API 계약과 서버 권한·업무규칙을 기능 단위로 함께 개발한다. Flutter용 인증·파일전송·기기 연동은 실제 앱 단계에서 추가 검증한다.
  • 데이터·API·운영 설계는 별도 문서에 있다. 공통 API 방향은 사용자 결정이며 구체 프로토콜·구현 기술·공급자는 미정이다.

원안대로 어르신마다 하나의 가족 공용 계정, 직원마다 개인 계정을 둔다. 가족 개인별 가입·초대는 기본 동선에 넣지 않는다. 센터는 확인된 전달 대상에게 계정을 안내하며 전달 경로·담당자는 운영 전 정한다. 가족별 로그인 기록이나 개별 가족 한 명의 권한 회수는 이 구조로 제공할 수 없다.

회수 제안: 직원 중지, 담당 해제, 공간 중단, 가족 비밀번호 변경 시 관련 권한 버전을 갱신한다. 기존 세션에서도 이후 API·파일 요청은 최신 상태로 재검사한다. 비밀번호 변경은 해당 공용 계정의 모든 기존 세션을 종료한다. 공간 재개는 이전 세션을 되살리지 않으며 다시 로그인한다. 이미 내려받았거나 화면에 표시된 사본의 회수는 보장할 수 없다.

복구 제안: 관리자가 비밀번호를 새로 발급하고 확인된 전달 대상에게 안내한다. 기존 비밀번호 조회·평문 보관·로그 기록은 제공하지 않는다. 가족 공용 비밀번호 변경 시 함께 쓰는 가족 모두에게 다시 안내해야 한다. 관리자 계정 분실·최종 관리자 퇴사에 대비한 복구 담당자는 운영 전에 지정한다. 기술 운영자의 일상 DB 수정을 복구 절차로 삼지 않는다.

초안은 허용된 네이버 블로그 호스트·경로만 설정하도록 제한한다. URL 리다이렉트·사설 IP·HTML 스크립트·과도한 응답을 거절하는 보호가 필요하다. 다른 블로그 서비스 지원은 별도 요청 시 확장한다.

처음부터 유지할 API 경계

UD-10은 API와 서버 업무규칙의 재사용 방향이다. 다음은 구체화 제안이며 아직 구현·검증된 계약 파일이 아니다.

  1. 언어와 화면에 독립적인 계약: HTTPS와 JSON 기반 업무 API, 안정적인 ID·날짜 형식·페이지 처리·오류코드를 문서화한다. 필요한 기능별로 OpenAPI 계약을 작성하고 구현과 함께 갱신한다. Flutter에 맞추려고 서버를 Dart로 만들 필요는 없다.
  2. 서버가 최종 판정: 대상 공간, 담당 배정, 공개 가능 여부, 첨부 한도와 삭제 조건을 서버가 확인한다. 웹·앱의 입력 검증은 사용자 안내이며 서버 검증을 대신하지 않는다. 현재 미정인 한도를 임의로 확정하지 않는다.
  3. 채널별 인증 전달과 공통 권한: 웹의 보안 쿠키/CSRF 보호와 앱의 토큰/안전 저장 등 전달 방식은 채널에 맞게 결정하되 같은 계정·세션 회수·권한 판정에 연결한다. JWT 채택이나 브라우저 영구 저장을 미리 정하지 않는다. 앱에 서버 비밀키를 넣지 않는다.
  4. 파일 처리도 API에 포함: 파일 선택 화면과 실제 전송 어댑터는 달라도 업로드 작업 ID, 상태 조회, 완료 확인, 공개·재시도·중복 방지와 접근 회수 규칙은 공통으로 사용한다. 저장소 직전송은 서버가 한정해 발급한 작업으로만 허용하는 안이다.
  5. 앱 업데이트 지연에 대비: 기존 필드·오류 의미를 유지하고 호환 가능한 추가를 우선한다. 호환성을 깨는 변경은 버전과 지원 종료 절차를 함께 정한다. /api/v1 같은 경로는 후보이며 구체 방식·지원기간은 아직 미정이다.
  6. 계약과 동작을 함께 검증: 브라우저 UI를 거치지 않는 독립 클라이언트로 조회·게시·업로드 상태 확인을 실행한다. 잘못된 공간·회수된 세션·중복 게시 요청도 같은 서버 판정을 받는지 검사한다. OpenAPI 문서나 생성 SDK만으로 호환성이 증명되지는 않는다.

재사용 대상은 서버의 API·권한·업무 규칙·DB·파일 처리다. 향후 추가할 것은 Flutter UI·앱 내 상태 관리·인증 저장 어댑터·카메라/파일 선택·알림 등 기기 연동·스토어 배포다. 모바일 전용 요구로 API가 확장될 수 있으므로 재개발이 전혀 없다는 약속은 하지 않는다.

개발 완료 판정에서는 웹이 공통 API를 실제로 사용하는지, 독립 HTTP 클라이언트도 같은 계약으로 동작하는지, 정책이 웹 전용 코드에만 남지 않았는지 확인한다. Flutter 전체 앱을 미리 만드는 대신 필요할 때 같은 계약을 호출하는 작은 연동 검증부터 수행한다.

참고: OpenAPI 공식 명세는 HTTP API를 언어에 독립적으로 기술하는 표준이다. Flutter 아키텍처 가이드는 UI와 데이터 접근의 책임 분리를 설명한다. 문서를 참고한 설계 제안이며 특정 표준 버전·SDK 생성기·프레임워크 채택은 별도다.

접근 판정

가족: 유효 세션 ∧ 센터 active ∧ 공용계정 active ∧ 공간 active ∧ 계정.space = 요청자료.space ∧ 가족 공개 상태.

직원: 유효 개인세션 ∧ 센터 active ∧ 계정 active ∧ 센터 일치 ∧ 공간 active ∧ 활성 배정 ∧ 요청 기능 허용.

관리자는 관리 기능 grant를 별도로 검사한다. 콘텐츠 열람은 담당 배정을 추가로 요구하는 제안이다. 목록 필터만으로 보호하지 않으며 단일 항목·파일·변환본에도 같은 판정을 사용한다. 요청의 space_id나 숨겨진 UI 값을 신뢰하지 않고 자료의 실제 소유 관계를 조회한다. 타인 자료의 존재를 알려주는 이름·파일 크기도 오류 응답에 넣지 않는다.

회수는 데이터 변경 커밋 이후의 새 요청부터 차단한다. 이미 전송된 바이트나 열린 화면을 원격으로 지울 수 있다는 보장을 하지 않는다. 파일 Range 요청과 재생용 파생본도 매 요청 권한을 검사한다. 브라우저/서비스워커의 민감 콘텐츠 영구 오프라인 캐시는 기본안에 넣지 않는다.

가족 조회는 published 버전만 반환한다. 담당 직원은 열람 권한으로 공개 버전을, 작성/편집 권한으로 해당 공간의 비공개 작업본·처리 중 첨부 상태를 확인한다. 권한 없는 가족의 view=draft 요청은 무시하여 권한을 높이지 않고 거절한다. 이는 게시 작업을 위한 초안이며 별도의 직원 전용 문서함 기능은 아니다. 이미 공개된 글을 편집할 때는 작업본과 공개본을 분리하고 전체 첨부 준비·확인 후 공개 버전을 교체한다. 잘못된 자료를 급히 내려야 할 때는 편집 완료를 기다리지 않고 철회한다.

로그인 화면에서 가족/직원 유형을 사용자가 조작해 권한을 얻지 못하도록 센터 내 login_id는 두 계정 유형을 합쳐 고유하게 검사하는 안이다. 계정 유형·역할은 서버가 결정한다.

미디어·게시 흐름

  1. 서버가 공간/기능·파일 선언·센터 잔여량을 검사하고 임시 전송 작업과 총량을 예약한다.
  2. 비공개 격리 위치로 전송한다. 객체 저장소 직전송 URL을 쓴다면 업로드 전용·단일 object key·짧은 유효기간으로 한정한다. 사용자가 열람하는 URL과 분리한다.
  3. 실제 파일 바이트·형식·악성 첨부·코덱·파생본 생성 결과를 검사한다. 지원되지 않는 형식은 이름 변경으로 우회하지 못하게 한다.
  4. 권한과 공간 상태를 다시 검사한다. 회수 뒤 도착한 바이트는 공개하지 않으며 작업 실패/정리 대상으로 돌린다.
  5. 전체 첨부가 준비되면 대상·동반 인물·내용 확인 후 게시 트랜잭션을 수행한다. 제목만 공개되거나 절반 파일만 보이는 상태를 만들지 않는다.
  6. 중단·실패 임시 파일과 용량 예약은 멱등 정리 작업으로 회수한다. 작업 장애 후 재실행해도 새 파일이 중복 생성되지 않도록 식별한다.

파일 전달은 인증 게이트웨이를 통한 매 요청 검사를 기본 검토안으로 둔다. 저장소의 presigned GET URL을 가족에게 직접 주면 유효기간 동안 소지자가 반복 사용할 수 있어 앱에서 권한을 회수해도 발급된 링크가 즉시 사라지는 것이 아니다. 운영비를 줄이기 위해 직접 링크 방식을 선택한다면 회수 지연 한계를 별도 결정·인수기준에 반영해야 한다. 현재 초안의 새 요청 차단 기준과 몰래 혼합하지 않는다. AWS 공식 URL 설명

삭제·복원 작업

접근 차단과 deletion_pending 기록을 먼저 커밋한다. 원본·파생본·변환 임시본·인덱스·캐시·저장소 버전을 작업목록으로 추적한다. 모두 확인되면 운영 저장소 삭제 완료로 기록한다. 백업 세대 만료가 남아 있으면 백업 대기 상태를 표시한다. 재시도는 이미 삭제된 객체도 성공으로 취급해 진행할 수 있어야 한다.

50명 기준 용량 산식

다음 수치는 이번 계산 예시이며 실제 사용량·허용량·견적이 아니다. 사진 공유본 1 MB, 영상 공유본 25 MB, 월 4.33주, 50명, 파생본 추가 30%를 가정한다. 6개월은 목업의 예정안을 비교하기 위한 가정으로만 사용한다. MB/GB는 10진 단위다.

월 신규 GB = 50 × 4.33 × (주당 사진 수 × 사진 MB + 주당 영상 수 × 영상 MB) / 1000

정상상태 공유본 GB ≈ 월 신규 GB × 보관 개월 × (1 + 파생본 비율)

예시1인 주당 사진/영상월 신규 공유본6개월 + 파생본 30%
낮음3장 / 0.25개약 2.00 GB약 15.62 GB
중간6장 / 1개약 6.71 GB약 52.35 GB
높음10장 / 2개약 12.99 GB약 101.32 GB

영상 0.25개는 4주에 1개 정도라는 집계 예시다. 원본 보존·DB·PDF·프로필·로그·백업·스토리지 버전·미완료 전송은 위 표에 포함하지 않았다. 실제 원본을 추가 보관하면 해당 용량을 별도로 더한다. 최근 자료만 보는지 과거 전체를 반복 다운로드하는지에 따라 전송량은 저장량과 달라진다.

월 전송 GB = Σ(자료별 실제 전송 바이트 × 요청 횟수) / 10^9 — 가족 수를 공용 계정 수와 같다고 가정하지 않는다. 영상 재생 중 Range 요청·재시도·캐시도 측정한다.

월 총원가 = 앱/DB/저장/요청/전송/영상처리/로그/백업/기타 서비스 비용 + 지원시간 × 내부 시간원가

기존 AI의 30,000원+2시간×80,000원=190,000원은 예시일 뿐 예산으로 옮기지 않는다. 공급자·리전·트래픽·지원 상한 결정 전 월가격을 확약할 수 없다. 센터가 비용을 최소화하려는 방향은 확인됐지만 무료 운영·무제한 지원을 뜻하지 않는다.

운영 부담을 줄이는 설계 제안

  • 업로드 개수·바이트·길이·보관 정책을 명시하고, 업로드 전 검사와 실패 파일별 재시도로 반복 문의를 줄인다. 영상 변환을 전혀 하지 않는 안과 제한 규격으로 변환하는 안의 기기 호환성을 비교한다.
  • 오류 알림은 실패 작업을 묶어 요약하고 비용·용량·블로그 실패·삭제 지연을 구분한다. 매 성공 게시 알림은 운영자에게 보내지 않는다.
